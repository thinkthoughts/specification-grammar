# SG_0001 — Specification Roles

Derived from `mathematical-basis/analysis/INVARIANT_EXTRACTION_MB_0001_0002_0003.md`, which compared three completed mathematical-basis specimens (MB_0001, number theory/counting; MB_0002, finite group theory; MB_0003, nonassociative algebra) built under three different verification regimes. This document proposes general roles from that evidence; it does not introduce a new YAML schema, and every proposed rule below cites the specimen(s) it's drawn from.

Provenance runs one direction: MB_0001/2/3 → observed invariants (in mathematical-basis) → proposed roles (here). This document does not bind back onto the specimens or require they change.

## 1. Observed invariants (summary; full evidence in the source analysis)

- A fixed seven-role envelope recurred exactly across all three: identity, state, provenance, specification, verification, result, and a closing principle/policy note.
- Within the specification role, a stable core recurred: the admissible domain, the leading claim itself, a list of positive constraints, and a list of excluded generalizations — plus exactly one domain-specific extension per specimen.
- A four-way independently-gradable state recurred (mathematical/computational/provenance/publication in MB's binding).
- Numerical or specific readings were always presented as consequences of a stated general specification, never as free-standing facts explained afterward — while the source analysis is explicit that this is a presentation-order fact, not a discovery-order one.
- Results were always captured (actual output, executable hash, run timestamp) rather than asserted, with unavailable provenance (commit hash) left null rather than fabricated.
- The role separation between justification (proof) and checking (verification) was not self-enforcing: MB_0001 and MB_0002 kept it clean from their first drafts; MB_0003's first draft violated it (its proof cited its own verification's output to close a step), and it took two rounds of review, not the directory layout alone, to fix.

## 2. Proposed SG roles

**SG-1. A specification names six distinct roles: Identity, State, Provenance, Specification, Verification, Result — and these roles need not be co-located in one artifact.** Evidence: the seven-key envelope, identical across MB_0001/2/3 (§1), where all six *are* co-located in one YAML per statement — but `analysis/SENSORS_BECKER_SG_AUDIT.md` (v4) found five of six roles present in sensors-becker's `RP_37` thread only once read as a composed system (RP YAML + extraction notebook + session report together); reading the specification artifact alone (as v1–v3 of that audit did) undercounted the same repository's own roles by half. Kept abstract deliberately — this document does not mandate that every SG-governed repository use these as literal YAML keys, or use YAML at all, or bundle all six into a single file. Mathematical-basis binds all six as keys inside one file; sensors-becker binds them across a thread of files. Both are valid bindings of the same six roles.

**SG-2. Independent aspects of a specification's state remain independently gradable — and this independence may be structural (distributed across nesting levels or across artifacts in a thread) rather than requiring one flat multi-axis field.** Evidence: MB's four-axis status (§1), where treating "proved" and "verified" as one collapsed axis in MB_0003 would have hidden the exact defect that review caught; and separately, `SENSORS_BECKER_SG_AUDIT.md` (v4), where `RP_37`'s thread showed three independently-moving status values — `identity.status` (static, template-level), `reading_point.status` (progresses developing→developing→complete across the A/B/C sequence), and per-dialogue-entry `status` (progresses candidate→admitted as later stages fold each one in) — at three different nesting depths within related files, not as one object. An earlier version of that audit (v1–v3) read only the flattest layer of sensors-becker's specifications and concluded independent gradability didn't hold there at all; reading the full thread reversed that finding. Not proposed as universal that every domain needs *these* axes, or needs them in *one place* — what's proposed as invariant is only that state is a set of independently-gradable dimensions, whether flattened into one object or distributed across a structure. Observed status-axis names may remain structurally stable while the vocabulary of values within an axis remains open to evidence from additional specimens: `analysis/INVARIANT_EXTRACTION_MB_0001_0002_0003_0004.md` found MB's four axis names held exactly across a fourth, structurally unlike specimen, while the `mathematical` axis's value set did not — MB_0004 required `audited` alongside `proved`, a value neither MB_0001–3 nor sensors-becker had needed. This says only that value-set closure shouldn't be assumed; it does not propose `audited`, or any other specific value, as part of a universal vocabulary.

**SG-3. A specification states both what constrains the admissible object and which extensions remain outside the claim.** Evidence: `leading_constraints` and `excluded_generalizations`, present with different content but the same structural role in all three specimens (§1). This is the single most directly transferable rule — the three specimens used it for three unrelated mathematical boundaries (squarefree-modulus scope, single-group scope, single-labeling scope), with the role itself unchanged. Not weakened by `sensors-becker`'s absence of this pattern: `SENSORS_BECKER_SG_AUDIT.md` (v4) confirms `RP_37`'s `engineering_constraints` list records facts about the engineering domain ("detector decay time limits count rate") rather than an epistemic boundary on the claim itself ("this statement does not cover X"). That's a genuine domain difference, not evidence against the rule — it suggests SG should eventually distinguish **domain constraint** (a fact about the object being engineered) from **claim boundary** (a fact about what a specification does or doesn't assert), as two different things that happen to share the word "constraint," rather than forcing sensors-becker's domain constraints to play MB's claim-boundary role. That distinction is noted here as future work, not resolved.

**SG-4. Discovery order and specification order are not the same thing, and a specification records the latter.** Evidence: MB_0001's actual history went numeral-first (24/25, corrected to 3) before the general C(m)=m/φ(m) form existed; MB_0003's 16 was found by enumeration before the rank-4 structural reason was found. In both cases the *finished* specification states the general form first and the number as its reading. This rule does not claim mathematics is discovered top-down — it claims a finished specification should make clear which statement is leading and which reading follows from it, regardless of which came first in the work that produced it.

**SG-5. Recorded results preserve the provenance actually available at the time of recording; unavailable provenance is left explicitly unspecified, not fabricated.** Evidence: all three `results/*.yaml` carry `commit_hash: null` with a comment explaining why, rather than a placeholder value someone could later mistake for real (§1). SHA-256 hashes, timestamps, and environment versions are implementation bindings of this rule, not the rule itself.

**SG-6. A specification's justification (proof) and its checking (verification) are distinct roles, and neither may silently stand in for the other — and verification itself has at least two depths worth telling apart: structural (did the process produce well-formed output) and content (is the claim itself correct).** Evidence for the first half: this is the rule MB_0003's first draft actually violated — its proof cited its own exhaustive verification's output as a necessary step in closing an unproven claim. The fix was not adding a `proofs/` directory (MB_0003 already had one); the fix was rewriting the proof's logical content so it no longer depended on the verification's result. Evidence for the depth distinction: `SENSORS_BECKER_SG_AUDIT.md` (v4) found `sensors-becker`'s `RP_37` notebook has genuine executable verification — it checks that every generated file exists, is non-empty, and has the expected structure — but this verification is entirely structural. It does not check whether the extracted engineering claims are correct. A real citation error (the source's organization misattributed in the downstream report) passed this verification cleanly, because the verification was never designed to check content against source. **This is proposed as a checklist question with two parts, not one**: *does this specification's justification cite its own verification's output as evidence for a step the justification has not independently established?* (MB_0003's failure mode) and separately, *does "verified" here mean the process ran correctly, or that the claim itself was checked against its source?* (sensors-becker's gap). A directory split, or a cells-labeled-"Verification" convention, answers neither question by itself; someone has to ask both.

**SG-7. Domain-specific content is an explicit extension point, not a gap to be standardized away.** Evidence: verification method (numerical sweep / exact enumeration / analytic derivation), justification weight (full paper / short proof file), and the relationship between a specification and its source (correction / independent re-derivation / extension past the source's own claim) all varied legitimately across the three specimens, and the source analysis found no common structure among them worth extracting (§1, "Explicitly NOT invariant"). SG should name this as a role that is *supposed* to keep varying, not treat the current lack of a common pattern as an artifact of having only three specimens so far.

## 3. Explicitly left domain-specific (not proposed for SG)

- The literal YAML key names mathematical-basis uses (`statement`, `status`, `source_provenance`, `specification`, `verification`, `result`, `footer`) — these are one binding of SG-1's roles, not the roles themselves.
- The specific four status axes MB uses (`mathematical`/`computational`/`provenance`/`publication`) — one binding of SG-2.
- Verification method, justification weight, and source-relationship type (SG-7).
- The specific closing sentence "Admissible generalizations trail leading specifications" — this recurred because all three specimens were written under one standing instruction in one project, not because three independent domains converged on the same sentence. Whether this belongs in SG as a named principle, or stays a mathematical-basis-specific convention, is unresolved and should not be assumed either way without evidence from a repository outside mathematical-basis.

## 4. Cycle 2 close and Cycle 3 selection criterion

The `sensors-becker` pressure test (Cycle 1) and the fourth MB specimen, MB_0004 (Cycle 2), are both complete. Status by rule: SG-1 reconfirmed on a fourth, structurally unlike specimen; SG-2 reconfirmed and narrowly extended (value-vocabulary openness, above); SG-3 remains the highest-priority unresolved question — two independent domains (sensors-becker's engineering constraints, MB_0004's in-domain theorem exceptions) have now each shown the current two-field pairing incomplete, in two different shapes, without yet showing what replaces it; SG-4 remains weakly evidenced, unchanged by MB_0004; SG-5 reconfirmed; SG-6 reconfirmed, with its structural/content depth distinction explicitly not merged with MB_0004's separate execution-success-vs-claim-coverage finding, which is held as an open hypothesis rather than folded in. SG-7 reconfirmed. Provenance's possible two-dimensionality (role × treatment of the source claim) is recorded as a hypothesis in `analysis/INVARIANT_EXTRACTION_MB_0001_0002_0003_0004.md`, not promoted to SG text.

Full reasoning for all of the above: `analysis/SG_0001_REVISION_MEMO.md`, frozen as the Cycle 2 decision record.

**Cycle 3 selection criterion, sharper than MB_0004's:** find a fifth specimen, ideally outside both graph theory and engineering, where object/domain constraints, epistemic claim scope, and some additional boundary mechanism can each be independently identified before formalization begins — the same discipline MB_0004 applied retroactively, applied in advance this time. That specimen should determine whether MB_0004's three-way structure (domain constraint / claim scope / exception set) generalizes, or whether SG-3 needs a more abstract formulation neither existing specimen has produced.
